# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

Files and commands on a server in the terminal: this machine's folder beside a server's, a transfer queue, and a Console (a shell on the server with a terminal), over the system's own `ssh` (SFTP for the files). Mooring is a keyboard-driven terminal app built with Ink (React for the terminal) on Node 22+, a sibling of Splice, Trawl, Sonar, Bosun, Hail, Keel, Wharf and Locker. Plain JavaScript ES modules with `.jsx` for components; no TypeScript, no linter config. The README is the user-facing spec; when behaviour changes, update it too.

It lives in the fleet repository, in `apps/mooring`, and is built on the fleet's shared kit, `@fleet/kit` (`packages/kit`; the root CLAUDE.md has its rules). Import the kit's files as `@fleet/kit/<file>`; Mooring keeps no copy of any of them, and a change to one is a change to every app, so run every app's tests (`npm test` at the root). Anything only Mooring needs lives in its own file. `src/app.js` tells the kit which app this is (`configureApp`: the name `mooring`, the title `Mooring`, the version a build bakes in); import `VERSION` and `COMPILED` from it. `src/theme.js` fills the kit's `theme` object with Mooring's palette (pink).

## Commands

```bash
npm install                                                    # once, at the repository root: every app and the kit
npm test                                                       # whole suite (node:test), here; npm run test:mooring at the root
node --import @fleet/kit/register.js --import ./src/app.js --test test/sftp.test.js      # one file
node --import @fleet/kit/register.js --import ./src/app.js --test --test-name-pattern="upload" test/*.test.js   # tests matching a name
npm start                                                      # run from the checkout (needs a real TTY and a host saved with /add)
npm run demo                                                   # a made-up host and machine (needs a real TTY)
npm run build                                                  # Bun-compiled executable for this machine → dist/ (the kit's scripts/build.js)
node scripts/logo.js                                           # regenerate assets/ from src/pet.js
```

`--import @fleet/kit/register.js` is required whenever Node loads `.jsx`; the tests also preload `--import ./src/app.js`. CI runs Mooring's tests on Linux and Windows whenever `apps/mooring` or the kit changes, so path handling and line endings must work on both. Nothing in the suite needs a server or `ssh`: the session tests run a stand-in SFTP server (`test/fixtures/fake-sftp-server.js`, speaking the protocol over a temporary folder) and a stand-in `ssh` (`fake-ssh.js`), through the same `spawn` the real code uses. Releases are automatic, as every app's (`mooring-v<version>`; root CLAUDE.md, "Releases"), with the version in `process.env.MOORING_VERSION`.

## Rules

- **Nothing secret is kept.** ssh runs with no terminal: `BatchMode=yes` (a key or the agent, and the host in known_hosts; it fails instead of asking) or, for a host saved with `password`, BatchMode off with a password asked for on every connect (`App` `connect` → `ctx.askSecret`, masked) and handed to ssh through `askpass.js`: `SSH_ASKPASS` and `SSH_ASKPASS_REQUIRE=force` name a script written to a private temporary folder (removed at exit) that prints `$MOORING_ASKPASS_PASSWORD`, which `createSession` puts in the environment of each ssh it starts and nowhere else (never an argument, a file, the config, a note, history, the activity log or a mood; `close()` lets go of it; `test/password.test.js` checks each). The Windows helper is a `.cmd` that has PowerShell print the variable, takes no argument and has no password in its text, since cmd would read an `&` or `%` as its own. `sftp.js` `problemFrom` turns ssh's words into what to do. The config holds hosts, key *paths* and whether a host asks for a password. The family's activity log and moods name hosts and files by the names shown, never a command (`$` commands can hold anything), a path's contents or a key.
- **A host key is trusted only by the user, one key, as shown.** `hostkeys.js` looks a host up (`ssh -G` for the files ssh reads, `ssh-keygen -F`, `ssh-keyscan`, `ssh-keygen -l`, all through `execFile`, never a shell) and `App` `trustHost` shows the fingerprint and asks before `trust` appends *that* line to the first file ssh reads; a host with any entry is never offered (a changed key stays ssh's error), nothing is asked when the tools are missing or the host doesn't answer, and a host name starting with a dash reaches no tool. Password mode adds `StrictHostKeyChecking=yes` so ssh itself never asks (its question would go to the askpass helper, which answers with the password, and the connection would hang until the timeout). `ssh -G`'s paths need `fixPath` (Git for Windows' ssh prints `/c/Users/…`, Windows' own `__PROGRAMDATA__`).
- **No native module** (the Bun build must keep working): the SFTP protocol is hand-written (`sftp-proto.js`), and what it needs from the OS is ssh and the clipboard tools the kit already uses.
- **A server's output is untrusted.** What `exec` returns goes through `format.js` `plainText` before it is drawn (escape sequences, controls); the Console's shell is drawn through the kit's `VirtualTerminal` (`@fleet/kit/vt.js`), which keeps only cells and styles: what it hands back for the real terminal (the bell, OSC 52's clipboard, titles) is dropped, never passed on; names from a listing are drawn as they are (the kit's `fit` and `Row` cut and clean them). A host's name or user starting with `-` is refused (`hosts.js`), as ssh would read it as an option.
- **Paths:** the server's are always `/` (`sftp.js`: `joinRemote`, `parentOf`, `resolveRemote`), this machine's go through the local object's own `join`, `parent` and `resolve` (`local.js`, and the demo's `/` twin), so nothing assumes a separator.

## Architecture

- **`src/sftp-proto.js`** (pure): SFTP version 3 (what OpenSSH speaks): `T`, `STATUS`, `OPEN`; `Writer` and `Reader` (strings, 32 and 64 bit numbers, attribute blocks; a short packet is a `ProtocolError`, not a crash), `FrameReader` (packets out of a byte stream, refusing a silly length), `kindOf`, `modeText`, `entryOf`.
- **`src/sftp-client.js`**: `SftpClient`, one open connection: requests by id, answers matched to them, `call` (a STATUS that isn't OK becomes a `SessionError` with `status`), and the operations (`realpath`, `stat`, `readdir`, `mkdir`, `rmdir`, `remove`, `rename`, `readlink`, `download`, `upload`). A transfer keeps 16 requests of 32 KiB in flight (`readAll` for reads: a short answer is asked again from where it stopped; EOF ends it; the file ending before its size said is an error), reports `onBytes`, keeps the modification time, and removes what it left when it fails or is cancelled. `openClient(host)` starts `ssh -s host sftp` (`sftp.js` `sftpServerArgs`) and returns once the server says its version; the process ending fails everything waiting with ssh's last words. Connections open now are ended when the process exits.
- **`src/transfer.js`**: whole folders over a client: `walkRemote`, `walkLocal` (links and special files skipped, never followed), `download` and `upload` (a file, or a tree with `recursive`; `onProgress({ bytes, total, file })` over the whole copy, the total known from the walk first).
- **`src/terminal.js`**: the Console's shell. `openTerminal({ host, spawn, columns, rows, dir, onChange, onExit })` runs `ssh -tt host <startCommand>` (`sftp.js` `terminalArgs`; `-tt` makes ssh force a terminal on the server although this side has pipes; the command is `stty cols C rows R; printf` of an OSC `5380` with `tty`'s path, `; cd '<dir>'; exec "$SHELL" -l`: the size is told at the start and the tty reported first, taken out of the output and believed only as a path under `/dev`) and returns `{ vt, write, resize, resizable, close, alive }`: ssh sends the server a window change only from a terminal of its own, so `resize(columns, rows)` fits the screen now (`VirtualTerminal.fit`, which keeps what is on it) and, once the size has stopped changing for 250 ms, runs `stty -F <tty> cols C rows R || stty -f …` from a second `ssh -T` (`sttyCommand`, `sshArgs`, the session's `spawn`, so key, agent and password hosts all sign in), one at a time, the last size winning; App calls it when the Console's room changes while it is showing. the output (and ssh's own messages on stderr) goes through a `VirtualTerminal` with 2000 lines of scrollback, `write` takes the bytes of the keys as they came. `test/terminal.test.js` runs it against `test/fixtures/fake-tty-ssh.js`; `demo.js`'s `terminal` is the demo's shell, answering what `exec` answers.
- **`src/session.js`**: `createSession(host)`, the interface the app uses (`home`, `list`, `mkdir`, `rename`, `rm`, `rmdir`, `get`, `put`, `exec`, `close`): the SFTP connection is opened by the first call and again after it drops (a call cut off by the drop fails and is never repeated by itself: it may have been done); `list` asks of each link what it points at (`isDir`, `link`); `exec` is `ssh -T host <command>`, one process per call, `onData` for output as it comes, a code of 255 (ssh's own) a failure; `terminal(options)` is `terminal.js` `openTerminal` over this session's `spawn` (so a password host signs in as for every ssh). `removeTree(session, path)` deletes deepest first. `src/demo.js` has the same interface (`demoSession`, with `state.calls` and `state.tree`; `chunks` and `tick` let a test stop a transfer half way) and `demoLocal`; a new operation needs both, and a test against `fake-sftp-server.js` in `test/client.test.js`.
- **`src/local.js`**: this machine's side: `createLocal({ dir })` with the same listing shape as the server's, plus `readText`, `hash` (sha256) and `watch` for syncing.
- **`src/queue.js`**: `createQueue({ session, concurrency, onChange })`: items `{ id, kind, name, from, to, recursive, size, status, bytes, total, error }`, `add`, `cancel` (a running one by its signal), `retry`, `remove`, `clear`, `idle`; `onChange` gets copies, progress throttled. The queue outlives a connection (App gives it a session that is whichever is open).
- **`src/sync.js`**: `/sync` and `/watch` (`actions.js` `sync`, `watch`, `uploadChanged`). Pure but for `walkTree` (a side's files as Map rel → { size, modified }, through `{ list, join }`: the session with `joinRemote`, or the local object) and the last sync's state (`loadBase`/`saveBase`, `~/.mooring/sync.json` keyed by `pairKey(host, localRoot, remoteRoot)`; sizes and times only). `planSync({ local, remote, base, direction, deletes, same })` is the plan (`upload`, `download`, `delete-local`, `delete-remote`, `conflict`, `extra`), `isIgnored` the ignore list (`DEFAULT_IGNORE` and `.mooringignore`, read through the local object's `readText`), `checksumCommand` the one `sha256sum` exec `--checksum` makes (the local side through `hash`). Transfers go through the queue (`modified` passed on, which the demo's `put` keeps), the folders they go into made first (`parentsOf`); deletes run in a task. After the queue is idle both sides are walked again and what matches becomes the base. `/watch` is App's `startWatch`/`stopWatch` (`ctx.watching`) over the local object's `watch(dir, onChange(rel))` (fs.watch recursive; the demo's `state.changed(rel)` stands in), changes collected for `WATCH_SETTLE_MS` and uploaded by `uploadChanged`; it stops on disconnect.
- **`src/health.js`** (pure): `/health` and alt+h (`actions.js` `health`, `healthRows`). `HEALTH_COMMAND` is one line for `session.exec` printing each part under an `@@name` marker (with fallbacks: `free -m`, `uptime`, no systemd), `parseHealth` reads it (names through `plainText`), `healthProblems` says what is wrong (a disk over `DISK_FULL`, failed units). The panel is a Viewer with `lines` and an `onKey` for r. App keeps the last read (`ctx.setHealth({ host, at, problems })`, cleared on disconnect), which `pet.js` `troubles` counts only for the connected host, so Tug's mood and `familyMood`'s reason say it. The demo answers the command with `DEMO_HEALTH`.
- **`src/hostkeys.js`**: `createHostKeys()` → `inspect(host)` (`{ known }`, `{ known: false, keys: [{ line, type, fingerprint }] }` strongest first, or `{ skip }`) and `trust(host, key)`; `App` takes it as the `hostKeys` prop (undefined in the demo). **`src/askpass.js`**: the helper script and the environment that makes ssh use it (above). **`src/hosts.js`** (pure): `parseTarget`, `parseAdd` (`password` as a word), `findHost` (name or unique prefix), `withHost`, `withoutHost`. **`src/sftp.js`** (pure): ssh's arguments, a server's paths, `sortEntries`, `problemFrom`, `shellQuote`. **`src/format.js`** (pure): sizes, rates, durations, dates, `plainText`.
- **`src/actions.js`**: every user-facing operation, written once; keys and slash commands call these with `ctx`. Everything that changes or removes something asks first (`ctx.confirm`; `danger` for a delete and a replace); `copyOver` is what `c` and `/get` and `/put` do, asking before replacing a file.
- **`src/commands.js`**: the slash-command table and completion (host names; the entries of a pane for `/get` and `/put`); your own commands (`usercommands.js`) come after them.
- **`src/ui/App.jsx`**: layout, focus, the prompt, overlays, the activity lines and **`ctx`** (read the `Object.assign(ctx, {...})` block before adding an action): `config`, `panes` (getter: `{ local, remote }` of `{ dir, entries, loading, marks, select }`), `conn`, `session`, `queue`, `loadPane(side, dir, { select })` (the listing replaces the old one only once it is read), `connect`, `disconnect`, `runRemote` (`$`), `task` (a visible, cancellable job), `note`, `confirm`, `askText`, `side()` and `setSide`, `toggleMark`. Focus (`side`) is read from a ref in the views' key handlers, as the prop may not have rendered when the next key comes. Uppercase shortcuts are alt+letter (`shortcutKey`), your keys (`keymap.js`) and `ctrl+p` go through `useKeyTranslation`.
- **`src/ui/*View.jsx`**: one component per tab: Files (two panes, each its own `useListNav`; `start` and `resetKey` put the cursor on the folder you came from), Transfers, Console (`consoleLines`: the shell's scrollback and screen as ANSI rows, the cursor a reversed cell; App owns the shell: `openShell`, `closeShell`, `enterTerminal`; while `focus` is `'terminal'` its `sendKey` hands every key, as it came, to the shell before any handler sees it, and ctrl+\ is the one key that leaves), Hosts, Log. Views check `ctx.viewHasKeys()` first in their `useInput` handlers.
- **The family** (`@fleet/kit/family.js`, shared): Mooring is in `FAMILY`, `ROLES` (SSH), `APP_NAMES` and `PET_NAMES` (Tug). `src/moods.js` (pure): `familyMood` (a transfer that failed or a connection that didn't open: worried; work running: busy) and `reactionTo` (Tug's line for a worried, sad or happy sibling, until esc). `familyMoods: false` turns both off; tests point `FAMILY_HOME` at a temp folder (`tempHome`). Deletes, renames, new folders and finished uploads go in the activity log through `ctx.task`'s `activity` and the queue's finish: what and which host, nothing more.
- **Environments** (`@fleet/kit/environments.js`, `src/environment.js`): App follows the project's chosen environment with `useEnvironment('mooring', cwd)` (`cwd` an App prop; the tests' `start` passes the temp home) and keeps it in `ctx.env`. Mooring's section is `{ host, folder }`: `openEnvironment` connects to that saved host (`findHost`) at that folder when the environment is switched, and at start when no `connectTo` is given. `askFirst(ctx, req, what)` is the production question (`productionQuestion`) before what changes the server: uploads (`copyOver` from the left), deletes and renames on the right, a `/sync` that uploads or deletes there, `/watch`. `runLine` calls `recordCommand('mooring', line)` for a slash command typed at the prompt (not your commands' expanded lines) unless it's in `NOT_RECORDED` (`/ssh`, `/run`): a command run on the server is never kept, as the activity log never keeps one.
- **Hosted mode**: `cli.jsx` takes its streams from `appTerminal()` and gives them to its TTY check, `terminalMouse` and Ink's `render`, draws on the alternate screen, and turns its self-update off when `hosted`. `apps/fleet/CLAUDE.md` has the protocol; Fleet hosts Mooring as its ninth space (`alt+9`, `ctrl+b u`: m is the folder move).
- **Updates** (`@fleet/kit/update.js`): once a day, the newest `mooring-v…` release; only in compiled builds, and off inside Fleet.
- **Theme and text**: a dark and a light palette in `src/theme.js`; every colour is read from `theme` while drawing; `@fleet/kit/text.js` (`fit`, `stringWidth`) for width-aware truncation, never `.length`.
- **Tug** (`src/pet.js`, `src/ui/Pet.jsx`): the sea otter's pixel art and mood (`moodFor`, from `troubles`: failed transfers, the connection's problem). `assets/` is generated from it by `scripts/logo.js`; don't hand-edit those files.

## Tests

`test/app.test.js` and `test/console.test.js` are end to end: they render `<App>` over `demoSession()` and `demoLocal()` with `ink-testing-library`, type keys into stdin and assert on `lastFrame()`, on the demos' state and on the family's folder (no command in it). `test/client.test.js` and `test/session.test.js` run the real client and session against the stand-in server (byte-for-byte transfers, short reads, cancelling, a connection that drops, ssh that fails before SFTP starts); `proto.test.js`, `sftp.test.js`, `hosts.test.js`, `format.test.js`, `local.test.js` and `queue.test.js` cover the pure parts. Use `until(check, what)` from `test/helpers.js` to wait for frames rather than fixed sleeps. Remember the kit swallows a bare uppercase key: tests send alt+letter (`\x1bg` for bottom).

## Keeping things in sync

Adding or changing a key or command touches several places: the handler (view or `App.jsx`), `src/commands.js` for slash commands, the `?` window's sections in `src/help.js`, the footer `HINTS` in `App.jsx`, and the tables in `README.md`. The tab numbers appear in `help.js`, `pet.js`'s `moodLine` and `FilesView.jsx`'s not-connected line. Commit messages are short sentences describing the change, without type prefixes.
