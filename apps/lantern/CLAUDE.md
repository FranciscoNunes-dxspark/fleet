# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

A web page audited in the terminal: it opens a URL in a headless Chrome found on the machine, measures it (Core Web Vitals, three runs, the median), runs axe-core in it, reads its DOM for the SEO basics and what blocks the first paint, checks its links, and lists what is wrong worst first; the security headers, cookies, mixed content, source maps and certificate through the kit's `webchecks.js`; Compare (two environments or two runs), the Waterfall of its requests, and the Domains view (DNS, redirects, https, the certificate). `lantern audit`, `lantern security` and `lantern domains` for a pipeline, with SARIF. Lantern is a keyboard-driven terminal app built with Ink (React for the terminal) on Node 22+, a sibling of Splice, Trawl, Sonar, Bosun, Hail, Keel, Wharf, Locker, Mooring, Bilge and Chart. Plain JavaScript ES modules with `.jsx` for components; no TypeScript, no linter config. The README is the user-facing spec; when behaviour changes, update it too.

It lives in the fleet repository, in `apps/lantern`, and is built on the fleet's shared kit, `@fleet/kit` (`packages/kit`; the root CLAUDE.md has its rules). Import the kit's files as `@fleet/kit/<file>`; Lantern keeps no copy of any of them, and a change to one is a change to every app, so run every app's tests (`npm test` at the root). `src/app.js` tells the kit which app this is (`configureApp`: the name `lantern`, the title `Lantern`, the version a build bakes in); import `VERSION` and `COMPILED` from it. `src/theme.js` fills the kit's `theme` object with Lantern's palette (amber).

## Commands

```bash
npm install                                                    # once, at the repository root: every app and the kit
npm test                                                       # whole suite (node:test), here; npm run test:lantern at the root
node --import @fleet/kit/register.js --import ./src/app.js --test test/audit.test.js       # one file
node --import @fleet/kit/register.js --import ./src/app.js --test --test-name-pattern="Compare" test/*.test.js   # tests matching a name
npm start                                                      # run from the checkout on this folder (needs a real TTY)
npm run demo                                                   # the demo shop and its staging copy (needs a real TTY)
node bin/lantern.js audit --demo                               # the headless audit, on the demo
npm run build                                                  # Bun-compiled executable for this machine → dist/ (the kit's scripts/build.js)
node scripts/logo.js                                           # regenerate assets/ from src/pet.js
```

`--import @fleet/kit/register.js` is required whenever Node loads `.jsx`. The tests also preload `--import ./src/app.js`. CI runs Lantern's tests on Linux and Windows whenever `apps/lantern` or the kit changes. Nothing in the suite starts a browser or reaches the network: the demo, a fake Chrome (`fakeBrowser` in `test/browser.test.js`), a fake spawn and local HTTP servers on 127.0.0.1 stand in. With a Chrome on the machine, `createLantern().audit(url)` against a local page is the manual check.

Releases are automatic, as every app's: a push to main that changes `apps/lantern` (or the kit, `patches/` or the root package files) releases it as `lantern-v<version>` (root CLAUDE.md, "Releases"). Compiled builds get the version via `process.env.LANTERN_VERSION`.

## Architecture

- **The provider** (`src/provider.js`): everything Lantern reads and does goes through one object, `createLantern({ fetchImpl, resolver, probe, find, launch, connect, axe, now })`: `pages(dir)`, `browser({ override })`, `audit(url, { runs, override, signal, onProgress, name, env, links })` → a page's result, `security(url)` (the kit's `checkSite`), `domain(host)` (the kit's `checkDomain`), `run`, `writeFile`. `src/demo.js` `demoLantern({ chrome })` has the same interface for `--demo` and the tests (`state.calls`, `state.written`); its security and domain checks are the kit's own over a stand-in network (`demoFetch`, `demoResolver`, `demoProbe`), its browser runs are canned raw runs fed to the same `assemble`. A new operation needs both, and its test.
- **The browser** (`src/chrome.js`, `src/cdp.js`, `src/browser.js`): **no Puppeteer, no Playwright, no browser in the build.** `findChrome` looks at the setting (`config.chrome`, or `LANTERN_CHROME`), then each platform's usual places (Chrome, Edge, Chromium); `launchChrome` starts it headless with `--remote-debugging-port=0` and a temporary profile, and reads `DevTools listening on ws://…` from its stderr (`--no-sandbox` only as root). `cdp.js` speaks the DevTools protocol over the runtime's global WebSocket (`cdpClient` over anything WebSocket-shaped, `connectCdp`). `runPage(client, url, { axeSource })` is one run in a fresh tab (flat sessions): `VITALS_SCRIPT` goes in before the page's own scripts (PerformanceObserver for LCP, CLS's largest session window, INP from event timing, FCP), Network events make the requests (a redirect kept as a row of its own), console errors and exceptions are kept, it waits for the load and half a second of quiet, clicks and presses a key for INP (0 when nothing took 16 ms), reads `FACTS_SCRIPT` (vitals, TTFB from navigation timing, title, meta, canonical, lang, images, links, what blocks the first paint) and, given axe's source, `AXE_RUN`. It decides nothing.
- **axe-core** is the one dependency beyond the family's: `axeSource()` is `(await import('axe-core')).source`, the package's own text of itself, which the Bun build carries inside the executable (checked: a compiled `lantern audit` runs axe in a real Chrome). It goes into the page on the last run only.
- **The judges** (`src/audit.js`, pure): `vitalsFindings` (Google's `THRESHOLDS`), `weightFindings` (weight, render-blocking, images), `a11yFindings` (axe's impact to severity, `wcagOf`), `seoFindings`, `consoleFindings`, `linkFindings` (`isBroken`: 404, 410, 5xx or no answer), `securityFindings` (the kit's, given the category); `medianVitals` over the runs; `assemble(...)` makes a page's result `{ url, name?, env?, at, chrome, lab, runs, vitals, samples, weight, requests, facts, console, a11y, links, security, findings, counts, note?, error? }`. Findings are the kit's findings.js shape plus `category` (perf, a11y, seo, security) and `selector`, `wcag`, `metric`, `value`, `helpUrl`, `host` where there are. `src/html.js` `htmlFacts` reads the same facts from HTML text, for a page audited without a browser.
- **Security** comes from the kit's `webchecks.js` (its header comment has the rules), shared with Sonar's `/domains`; keep checks that need no browser there, not here. `src/security.js`: `sarifOf`, `withoutIgnored` (a rule, or `rule:url`, or `rule:host`).
- **Pages** (`src/pages.js`): `readPages(dir)` from `lantern.json` (`pages`/`urls`, `domains`) and each environment's `lantern` section in `.fleet/project.json` (`url`, `urls`; the kit's `readProject`); `normalUrl`, `pathOf`, `counterpart` (the same path in another environment, for Compare). **`src/history.js`**: the last three results of each URL in `~/.lantern/runs.json` (`addRun`, pure).
- **`src/failon.js`** (pure): `parseFailOn` (levels, `category:level` with axe's words, `perf:<metric>><value><unit>`) and `failures(result, terms)`. **`src/headless.js`**: `HEADLESS`, `runHeadless(args, { provider, config, write })` resolves the exit code; `audit` (its own JSON, the pages one after another: their vitals are measured in the one browser), `security` and `domains` (the kit's `securityJson`, which Fleet reads: keep its shape; their pages and hosts checked `CHECKS_AT_ONCE` at a time through provider.js's `pool`, printed in the order asked, as `/domains` does), `--sarif` through `output`.
- **`src/share.js`** (pure): `requestContext` (Hail's `request` context: method, URL, what came back, never headers), `compareRows`, `compareSentence`, `sideLabel`, `delta`, `markdownReport`.
- **`src/actions.js`**: every user-facing operation, written once. **`src/commands.js`**, **`src/help.js`**: the slash commands and completion; the `?` window.
- **`src/ui/App.jsx`**: as Bilge's (its CLAUDE.md), with `ctx` holding `pages` and `hosts` (getters), `selectedPage()`, `select(i)`, `setPages`, `addPage` (`/open`'s, kept for the session), `addResult` (into the history, saved), `resultFor(url)`, `runsOf(url)`, `latestResults()`, `shownFindings(result)` (without `config.ignore`), `setDomain`, `setCompare`, `setFilter`. Nothing is audited on opening (it starts a browser); `ctrl+r` audits the selected page again. The top line says when no browser was found. Lantern draws in the kit's shell look (`look: 'shell'` in `src/app.js`, the kit's `look.js`): the top line (`topLine`: Flit's face, the views, `headerContext` at the right), the view, the activity, a one-row prompt, and the status line (`StatusLine`: what Flit says, the keys); the welcome is the status line's message until the first command, and Flit's pixel art shows in the empty Pages view.
- **`src/ui/*View.jsx`**: Pages, Findings (`f` category, `s` severity), Compare (`compareSides`: the selected page and its counterpart in another environment, two runs, or two URLs), Waterfall (`barCells` in rows.js), Domains, Log; views check `ctx.viewHasKeys()` first and read the cursor's row with `nav.current()` inside their key handlers.
- **The family** (`@fleet/kit/family.js`, shared and never edited here; `src/moods.js`, pure): Lantern is in `FAMILY` (role `WEB`, Flit). It takes the `page` context (`/take` audits its URL); `t` copies one (URL, environment, how many findings); `↵` in the Waterfall hands Hail a `request` through `copiedNote`. Audits and domain checks go to the activity log (URL and counts only); `/env` is the kit's `setEnvironment` and selects the environment's first page; `submit` calls `recordCommand('lantern', line)`; Flit's mood to `writeMood`; tests point `FAMILY_HOME` at a temp folder (`tempHome`).
- **Config** (`src/config.js`): `~/.lantern/config.json`, overridable with `LANTERN_HOME`. Change it only through `ctx.setConfig`.
- **Updates, hosted mode, mouse, theme and text**: as Wharf's (its CLAUDE.md).
- **Flit** (`src/pet.js`, `src/ui/Pet.jsx`): the moth's pixel art and mood. `assets/` is generated from it by `scripts/logo.js`; don't hand-edit those files.

## Tests

`test/app.test.js` and `test/family.test.js` are end-to-end: `<App>` over `demoLantern()` with `ink-testing-library`, typing keys and asserting on `lastFrame()` and `provider.state`. `test/audit.test.js` covers the judges, the median, `htmlFacts`, `assemble`, `--fail-on`, Compare's rows and sentence, the request context and the report; `test/browser.test.js` the CDP client over a stand-in socket, `runPage` against `fakeBrowser`, finding and launching Chrome with a fake spawn, `axeSource`, and the provider end to end with the fake browser and a local server; `test/headless.test.js` the three headless commands (text, `--json`, `--sarif`, exit codes) and a folder's pages. The kit's `test/webchecks.test.js` covers the security and domain checks. Use `until(check, what)` to wait for frames rather than fixed sleeps.

## Keeping things in sync

Adding or changing a key or command touches several places: the handler (view or `App.jsx`), `src/commands.js` for slash commands, the `?` window's sections in `src/help.js`, the footer `HINTS` in `App.jsx`, and the tables in `README.md`. Commit messages are short sentences describing the change, without type prefixes.
