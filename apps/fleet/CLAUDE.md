# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

Fleet (`apps/fleet`, package `@fleet/host`, binary and releases `fleet`, tags `fleet-v…`) is the host: one terminal program that runs the family's eight apps (Splice, Trawl, Sonar, Bosun, Hail, Keel's terminal app, Wharf, Locker) and switches between them with a prefix, `ctrl+b` like tmux's (host.json's `"prefix"` or `FLEET_PREFIX` names another; `ctrl+]`, the first one, which is hard to type on many keyboards, always works too). Plain JavaScript ES modules; the host itself draws with escape sequences, not Ink. The README is the user-facing spec; when behaviour changes, update it too. The root CLAUDE.md has the repository's rules (the kit, CI, releases).

## Commands

```bash
npm test                                                       # here; npm run test:fleet at the root
node --import @fleet/kit/register.js --import ./src/app.js --test test/keys.test.js     # one file
npm start                                                      # run from the checkout (needs a real TTY): node bin/fleet.js [app] [args…]
npm run build                                                  # Bun-compiled executable for this machine → dist/fleet-<platform>, all eight apps inside
node scripts/logo.js                                           # regenerate assets/ (the container ship)
powershell -File installer\build.ps1 [-Version 1.2.3]        # Windows, after npm run build: dist\fleet-windows-x64-setup.exe (needs Inno Setup 6)
```

## Design

**Each app stays its own process.** Running them in one process would break the kit's per-process state (`configureApp` is the app's name for credentials, releases and the version; `theme` is one object), so the host starts each app as a child. No pty either (the Bun builds can't carry node-pty): the child gets pipes, and runs in **hosted mode** (the kit's `hosted.js`), which makes them look like a terminal to Ink.

**Hosted mode** (`packages/kit/hosted.js`, on when `FLEET_HOSTED=1`): every app's cli takes its streams from `appTerminal()` (process.stdin and process.stdout outside the host, with only ctrl+v's paste and Windows' console's characters added) and gives them to the TTY check, `terminalMouse` and Ink's `render({ stdin, stdout })`; with `hosted` it also leaves the self-update off (the fleet binary updates as one). Inside the host, `hostedStreams` gives those pipes `isTTY`, a no-op `setRawMode` (whose first call tells the host the app reads keys), `columns`/`rows` (from `FLEET_COLUMNS`/`FLEET_ROWS` at start, then the host's messages) and `'resize'`. It also keeps the app's screen (`screenKeeper`: from the last frame Ink's log-update wrote, or the last clear, plus what came after, without OSC sequences or the bell), because Ink only draws what changed: the host's repaint is that screen written again. When the control pipe ends (the host quit or died) the app exits by itself (`process.exit(0)`, so its own exit handlers run, Bosun's stopping its crew). Everything else the app does (config, credentials, its name and version, `familyHome`, mouse reports, OSC 52 and 9, the bell) goes through stdin and stdout as it always did, and the host passes it on.

**The control pipe** is fd 3, newline-delimited JSON from the host to the app (`encodeMessage`, `messageReader`). Node reads it as a socket; Bun can't wrap fd 3 in one, so in the compiled build it's read with `fs.createReadStream`. The app's messages go the other way inside its stdout, as `ESC ] 5379 ; <json> BEL` (`encodeAppMessage`), which `screen.js`'s `OutputFilter` takes out and hands to the host (`decodeAppMessage`), on screen or not: on Windows a child's writes to fd 3 never reached the host, while its stdout always does.
- host → app: `{ "resize": { "columns", "rows" } }`: the size to draw at; the same size again means repaint (the kept screen is written at once); a new size emits `'resize'`, and if Ink draws nothing new within 60 ms the kept screen is written again.
- app → host: `{ "ready": true }` (Ink started reading keys), `{ "handoff": "trawl" | [apps], "line": "…" }` `{ "update": true }` (an app's `/update`, `askHostToUpdate` in `hosted.js`: the host looks for a new Fleet now, whatever the daily check said, and installs it, saying so in the bar; `cli.js` `updateFleet`) and `{ "move": "/abs/folder" }` (`askHostToMove(dir)` in `hosted.js`, the folder made absolute in the app: the host's bar asks to move the fleet there, prefilled, and moves it only on ↵; `Host.message` → `askFolder`).

**Hand-offs**: every app says `copiedNote(apps, line)` (the kit's `family.js`) right after copying a line for a sibling, so that's where `handOff` tells the host. The host (`handoff.js` `routeHandoff`: one app, or the first running of several) switches to that app, starting it if needed, and once it's `ready` (300 ms after, for its views to settle; 100 ms after a switch to one already running) writes the line into its stdin in one write, which the apps' paste rule (`pastedLine`) puts in the prompt. The apps don't read bracketed paste, so it's plain text, line breaks taken out.

## Architecture

- **`src/main.js`**: the entry point (bin/fleet.js from a checkout, the build's `entry`). It imports nothing up front, because `fleet --run <app> [args]` makes the process that app: it takes `--run <app>` out of `process.argv` and imports the app's cli (`../../<app>/src/cli.jsx`, Keel's `cli/cli.jsx`), which must be the first to call `configureApp`. `fleet mcp` and `fleet --mcp-worker <app>` go to `src/mcp/` (below). Anything else imports `cli.js`, the host.
- **`src/cli.js`**: the host's command line (`fleet [app] [args…]`, `-v`, `-h`), the TTY check, raw mode, the kit's `plainOutput` (in Windows' own console the characters its font lacks are swapped as everything, the apps' output too, goes out), the first space (named, else `host.json`'s last, else Splice), cleanup (every app stopped and the terminal given back however the host ends: `exit`, `SIGTERM`, `SIGHUP`, an uncaught error), and its own update check (compiled only, the kit's `update.js` under the name `fleet`).
- **`src/spaces.js`**: the eight spaces (`id`, `title`, `letter`, `accent` from each app's theme) and `launchCommand`: from a checkout `node apps/<app>/bin/<app>.js`, as the app's `npm start`; compiled, the executable itself with `--run <app>`.
- **`src/launch.js`**: `appSpawner` starts an app in the folder the host says (`cwd`, with `PWD` to match) with stdio `pipe` ×4 (stderr kept for the exited screen, fd 3 the control pipe), in its own process group off Windows, with `appEnv` (hosted mode, the size, and `FORCE_COLOR` from the terminal's colour depth, since colour libraries see a pipe). `killTree`: SIGTERM, or SIGKILL to the group; `taskkill /T /F` on Windows.
- **`src/keys.js`** (pure): `prefixByte(name)` (`ctrl+b` → `\x02`; null for one a terminal keeps, as `ctrl+c`, `ctrl+m`, `ctrl+s`), `prefixName(byte)`, `prefixesFor(byte)` (it and `ctrl+]`, `PREFIX`), `DEFAULT_PREFIX`. `readKeys(state, input, spaces, prefixes)` → `{ state, actions }` (`state.prefix` is the prefix byte typed, so the same one again is sent to the app): `send` (everything but the prefix and its key, unchanged), `switch`, `move` (next or previous), `split`, `unsplit`, `pane`, `folder` (the prefix and m), `quit`, `help`, `runbooks` (`r`), `trace` (`f`: `t` is Trawl's), `prefix`. The key after the prefix is a whole escape sequence where it is one, so an arrow can't leak `[A` to the app. `takeBarClicks` takes SGR mouse reports on the bar's row out of what goes to the app.
- **`src/bar.js`** (pure): `barLayout` (tabs, state marks and badges, the hint or the prefix's keys or a notice; widths through the kit's `text.js`; names shrink to letters, then the line is cut), `tabAt` for clicks, `renderBar` (the accent in 24-bit colour, else the nearest of 256).
- **`src/screen.js`** (pure): `OutputFilter`, one per app, passes its output through and drops what would break the shared screen (the alternate screen 47/1047/1048/1049, the title stack `CSI 22/23 t`, `ESC c`), keeps the modes it set (mouse, cursor, focus, bracketed paste) for `restoreModes` on a switch (which also sets the host's own mouse, `HOST_MOUSE`: clicks as SGR reports, kept on whatever the app does, so the bar's clicks always arrive; an app turning 1000 or 1006 off only stops its own reports, `wantsMouse`, and `Host.deliver` passes mouse reports only to an app that wants them), never cuts an escape sequence (a partial one waits for its end), and puts the bar in where it's safe: just before a synchronized update ends (`CSI ?2026l`), else at the end of a chunk when nothing is open (no sequence, no sync, no saved cursor of the app's own).
- **`src/host.js`**: `Host`, with everything injected (`input`, `output` with columns/rows/'resize', `spawn`, timers). The apps get every row but the last. `switchTo` clears the screen, sets the app's modes, draws the bar and sends the app its size (the repaint), or starts it the first time; inactive apps keep running, their output only read for their modes. An app that exits shows "<App> exited — ↵ to start again" with the end of its stderr. Help is an overlay (the app's output is held back until it closes, then repainted); so is a panel (`overlay`, below), which also takes every key while it's open (`showOverlay`, `closeOverlay`; `redraw` draws it again rather than the app while it's open, so the help and a resize come back to it). `sendLine(id, line)` is a hand-off's second half (switch, start, type once ready), which runbooks use too; `typeInto(id, line)` types a line into an app's prompt without switching to it (now when it's ready, else once it is). `lastRequestId` is the request the last hand-off named (`trace.js` `requestIdOfLine`), which the prefix and `f` offers. `prefix` is the byte `cli.js` read from host.json (`prefixLabel` its name, in the bar's hint, the help, the exited screen and the trace panel). A panel over a split stays on top: the panes don't draw while it's open, and are drawn again from their virtual terminals when it closes. The split view is below. `quit` ends every control pipe (the apps quit by themselves), kills what's left after 3 s, and writes `LEAVE`.
- **`src/attention.js`**: the badges. `familyReader(dir)` reads the family's folder (the kit's `familyDir()`: `FAMILY_HOME` or `~/.family`), each space's `<id>.mood.json` and the end of `activity.jsonl`, a file again only when its size or time changed; `badgeFor` (pure) gives a space `!` while its mood is worried or sad and became so after `seen` (when the space was last on screen; Fleet starting counts), and a count of entries of the `ALERT_KINDS` (`alert`, `error`, …; most entries are `info` or `change`) logged since. Spaces are keyed by id, which is the app's name in those files, so a new app writing moods (Keel's terminal app) needs nothing here. `Host.checkAttention` runs every `attentionEvery` ms (3 s; the tests' 100), sets each space's `badge` (the spaces on screen never have one: `looked` clears it, on switching to and away from a space), and for a new one rings the bell (`bell`: off with `FLEET_NO_BELL=1` or `host.json`'s `"bell": false`) and puts the reason in the bar's notice.
- **`src/folder.js`**: moving the fleet. `editLine` (pure: a line editor over what's typed, saying `submit`, `cancel` or `complete`), `completeFolder` (tab: one folder whole, several as far as they agree; `readdir` injected), `resolveFolder` (`~`, relative to the fleet's folder), `shortFolder`, `renderAsk` (the bar while it asks; the default hint gives way to the line, a hint that says something keeps up to half). `folderPicks(cwd, recent)` (the kit's `folderChoices`, `isProject` marking projects) is the folder panel's list (panels.js `FolderPanel`, the prefix and m: typing a folder first, which is `askFolder`, then each folder, `overlay.js` `folderLines`; the window's Move dialog gets it from the server's `folder-list`). `Host.askFolder` puts the bar in that mode (`asking`: every key goes to the editor), `moveTo(dir)` sets `Host.cwd` (what `launch` passes to `spawn`) and puts it first in `folders`, and ends each running app's control pipe with `moving` set, so its exit launches it again at once (killed after 3 s, as quitting does). `cwd` isn't saved in `host.json`; the folders moved to are.
- **`src/vt.js`**: `VirtualTerminal`, the split view's screen per pane: cells of a character (a grapheme, wide ones taking two cells) and a style (SGR parameters, `''` for none), from what Ink and the apps write (text with the tty's `\n` → `\r\n`, cursor movement, erase with the background in use, insert and delete, scrolling and its region, save and restore, 16/256/24-bit colours and the colon forms, private modes, synchronized updates). `write` returns what is the terminal's rather than the pane's (the bell, OSC 52, 9, 777 and titles) for the host to pass on; hyperlinks and other strings are dropped. `rowAnsi(y)` draws a row whole, ending with a reset; `takeDirty` says which rows were drawn on. `test/vt.js` is a different, smaller model: the test terminal, which checks what the host drew.
- **`src/split.js`** (pure): `splitLayout` (two panes, a one-column divider at the left one's width), `paneAt`, `takePaneMouse` (SGR reports taken out of the input by pane, moved into its columns, with `press` for the clicks that focus it), `MIN_SPLIT_COLUMNS` (40).
- **`src/state.js`**: `~/.fleet/host.json` (`FLEET_HOME`): `last`, `update`, `bell` and `prefix` (read only), `folders` (the move's list, newest first, the kit's `folders.js` `remember`: `Host`'s and `GuiSession`'s `folders` and `onFolders`).
- **`src/panels.js`**: `Panels`, made by `Host` with its `tools` option (`cwd`, `env`, `takers`, `familyDir`, `bosun`, `now`; the tests point them at temp folders), and its two panels, each `{ render(size), keys(text) }`. The runbooks: a picker (`n` drafts one) and a runbook whose `↵` marks the step done and calls `host.sendLine`; the runbook open and each one's progress (by file) are kept for the session, and the files read again on every open. The trace: a one-line field (prefilled from `host.lastRequestId`), then `follow(id)`: `host.typeInto` with `traceLine(id)` for each running space in `takers` (`TAKEN_BY.logline`), and `traceTimeline`. Fleet never sends `↵` after it: an app with a question open would take it as the answer. `panelKeys` names the keys.
- **`src/runbooks.js`**: `parseRunbook` (pure: a step per line of a fenced block whose info string is a space's id, the prose before a block on its first step, the first `#` heading the title, other blocks prose), `runbookDirs` (the start folder's `.fleet/runbooks`, its checkout's, `fleetHome()/runbooks`), `listRunbooks`, `draftRunbook` (pure, from `readActivity`'s entries: they are descriptions, not commands, so a "What happened" list and an empty block), `writeDraft` (`<date>-draft.md`, never over another).
- **`src/trace.js`**: `traceLine(id)` (a `logline` context `{ process: 'trace', text: id, requestId: id }`: Sonar and Hail look by `requestId`, Bosun and Wharf by the text too), `requestIdOfLine`, and `traceTimeline(id, { familyDir, bosun, since })`: activity entries and Bosun's session lines (`<bosun home>/sessions/*/*.jsonl`, `recorder.js`'s format, read here without importing Bosun) that mention the id, oldest first. `bosunHome` is Bosun's `configDir` (`BOSUN_HOME`).
- **`src/overlay.js`** (pure): the panels' rows as segments, `boxRows`/`boxSize`/`scrollFor`/`placeBox` (a box as wide as the screen allows up to 100 columns, every row but the bar's less one above and below, scrolled to the cursor, `⋯` in a border when there's more), `pickerLines`, `runbookLines` (the app's name in its accent), `traceAskLines`, `traceLines`.
- **`src/gui/`**: `fleet gui` (main.js imports `gui/cli.js` only then, after `app.js`). `session.js` `GuiSession` is the host without a terminal: each app spawned as `launch.js` does (with `FLEET_GUI=1` besides hosted mode), its output through its `OutputFilter` into a `VirtualTerminal` (vt.js) at its pane's size, and `frame` events (`frames.js` `rowRuns`: a row as `[column, text, style, cells]` runs, a wide character its own run) for the rows that changed, at most every 16 ms and never inside the app's synchronized update; `snapshot()` is everything a window opening now needs. It keeps what Host keeps (ready, hand-offs through `routeHandoff`, typing a line once an app reads keys, exits, restarts, `moveTo`, badges through `attention.js`) and turns what the app said to the terminal (`vt.write`'s return) into `bell`, `copy` (OSC 52), `notify` (9, 777) events; an app's `{ view }` messages (the kit's `GuiView`) are kept per space and sent as `view` events. `server.js` `guiServer` is the HTTP side: 127.0.0.1 only; the run's token, from the printed address once (then an HttpOnly SameSite=Strict cookie, the address cleaned by a redirect), for every request; the Host header must be the loopback address (DNS rebinding); POSTs to `/api/<action>` need `x-fleet: 1`; `/events` is server-sent events (`hello`, then the session's events); the page has a CSP with no inline script. Its actions are the window's (`show`, `resize`, `input`, `restart`, `move`, `folders`, `runbooks`, `runbook-step`, `runbook-draft`, `trace`, `trace-last`), the runbooks' progress kept per file for the session. `loadClient` reads the window's files from `gui/` and the apps' logos (`LOGOS`) in a checkout, else from `assets.js`, which `scripts/gui-assets.js` writes for the compiled build (and `test/gui-assets.test.js` checks is current: run it after changing `gui/` or a logo). `cli.js` parses `fleet gui [--port] [--no-open] [--print-url] [app [args…]]`, opens an app window of a Chromium-family browser when there is one (`openWindow`), and stops everything on a signal or, with `--print-url` (Fleet Desktop), when stdin ends.
- **`gui/`**: the window, plain ES modules loaded by the page, no build: `app.js` (the rail, panes and their screens, keys through a hidden textarea and the document, the mouse as SGR reports for an app that wants it, drawers, dialogs, the palette, notifications, `window.fleetDesktop`'s commands), and the pure parts the tests load too: `keymap.js` (a keydown or a mouse event → a terminal's bytes), `sgr.js` (a style → CSS), `boxes.js` (the box-drawing and block characters the page draws with CSS so they meet), `views.js` (the native views: `chartSvg`, `chartLayout`, `pointAt`). Rows and runs are positioned by cell (`--cw`, `--ch`, measured from the font), so a font's widths can't push a row out of line. Native views draw under the text layer, at their cells.
- **`src/mcp/`**: `fleet mcp [--project <dir>] [--demo]` (main.js imports `mcp/server.js` only then), an MCP server for Claude Code over stdio on the kit's `mcp.js` (hand-rolled JSON-RPC, as Trawl's; stdout is protocol only, so `quietConsole` sends console.log to stderr). Read-only, always: one module per app, each a list of `{ name, description, inputSchema, run(args, ctx) }` over that app's own modules, imported when a tool first runs (`git.js`: Splice's `git.js` runner and `parse.js`, revisions checked so none passes as an option; `bosun.js`: Bosun's recordings through `recorder.js` `listSessions` and `replay.js`; `hail.js`: `http-file.js`, `history.js`; `sonar.js`: Sonar's `azure/arm.js` and `az.js` and `insights.js` queries, or `demo.js`; `wharf.js`: `docker.js` and `kube.js`, only their reading calls; `family.js`: the kit's `family.js`). `server.js` passes every answer, and every error, through `bound.js` `finish`: the kit's `redactSecrets`, then at most `MAX_TEXT` characters. These modules never call `configureApp` or import an app's `app.js`: this process is Fleet. What must be its own app runs in a child (`proxy.js` `childServer`, an MCP client): Keel's tools (`keel.js`) in `fleet --mcp-worker keel` (main.js imports Keel's `cli/app.js` first, then `mcp/worker.js`; it builds Keel's service as `cli/service.js` does but without the production monitors' background checks, and refuses to fall back to Keel's demo organization when none is set up), and Trawl's are Trawl's own `trawl mcp`, started as the host starts Trawl (`launchCommand`) and listed under `trawl_`. Compiled, both children are the executable itself (`--mcp-worker keel`, `--run trawl mcp`). A new tool: an entry in its app's module with a JSON schema and a description of what comes back, a row in the README's table, and a test.

**The split view** (`Host.split`: `{ panes: [{ id, x, width, vt, drawn }], focus, modes }`, null when whole): `active` is the focused pane's app, keys go to it alone. Each pane's app is told its pane's size (`sizeFor`) and its output goes through its `OutputFilter` (messages, modes, the alternate screen dropped) into the pane's `VirtualTerminal` instead of the terminal (`fromPane`); `flushPane` then writes the rows that changed since they were last drawn (`drawn` keeps each row's last ANSI) at the pane's columns, in one synchronized update, waiting while the app's own synchronized update is open, and puts the cursor where the focused app has it. `redrawSplit` (a switch of focus, the help closing, a resize) draws everything from the virtual terminals, with no round trip to the apps; the divider is in the focused app's accent; the terminal's modes are the focused app's (`split.modes`, written again when they change). Switching to an app while split (`showInPane`) focuses its pane or puts it in the focused one, with a fresh virtual terminal and a resize (a repaint at the same size), and the app leaving the screen is told the whole size again. Mouse reports go to the app under the pointer when it wants them, moved into its columns, and a press focuses that pane (`deliverSplit`). Exits draw `exitedScreen` into the pane; a restart there resets its virtual terminal first (the app's alternate screen, which would clear it, never gets that far). A hand-off from a pane to an app in neither opens it in the other pane. Below `MIN_SPLIT_COLUMNS` the screen won't split, and a resize below it unsplits. Unsplit (`unsplit`), the focused app is told the whole size and draws straight to the terminal again, as before: the whole-screen path doesn't touch the virtual terminals at all.

**Why the bar is drawn again rather than kept out of the apps' way**: Ink draws whole frames and, in the full-screen case, starts each with clearing the terminal, which a scroll region wouldn't stop; and the apps' frames are a row shorter than their screen, which ends with a newline onto the row below, which inside a scroll region would scroll it. So the apps draw on rows 1 to rows−1 of the whole screen, and the bar is written again after each of their frames, from a saved cursor (`ESC 7` … `ESC 8`, which keeps the app's cursor and colours), inside the frame's synchronized update when it has one, so the terminal never shows a frame without it.

## Version and build

The kit's `scripts/build.js` reads `"fleet"` in package.json: `entry` `src/main.js`, `compile` off Bun's `.env` and bunfig loading (Keel's server code is inside), and `includes`, the eight apps' folders: each one's `process.env.<APP>_VERSION` is defined from its own package.json, as each app's `src/app.js` reads it, beside `FLEET_VERSION`. So inside the build every app is `COMPILED` with its own version (Keel keeps its data in `~/.keel` as its own build does), and none updates itself, since each cli turns updates off in hosted mode. Releases are `fleet-v…`, made whenever any app, the kit or Fleet changes (`.github/scripts/changed.mjs` adds Fleet to any app's change).

## The Windows installer

`installer/` builds `fleet-windows-x64-setup.exe`, which the Release workflow publishes beside the executables (`release-app.yml`, Fleet's Windows build only). `build.ps1` downloads the portable Windows Terminal pinned in `terminal.json` (the same release as Harbor's `Setup.cs`; moving to another means its version and SHA-256 there), checks it, marks it portable (`.portable`), and runs Inno Setup on `Fleet.iss`. The setup installs per user into `%LOCALAPPDATA%\Programs\Fleet` (fixed: `settings.json`'s Fleet profile names `fleet.exe` by that path), `fleet.exe`, `fleet.ico` and the terminal in `terminal\`, with `settings.json` (a Fleet profile, a font list, ctrl+c/ctrl+v as copy and paste) written only when there isn't one. The Start menu shortcut starts `WindowsTerminal.exe -p Fleet` in the folder picked in the setup (the profile's `startingDirectory` is null, so the terminal starts where the shortcut says), with an AppUserModelID of Fleet's own, so the terminal's windows go under its button. Fleet updates `fleet.exe` there itself, and `fleet.ico` with it (the shortcuts' icon, which the new executable alone wouldn't change): the Release workflow publishes `fleet.ico` beside the executables (Fleet's Windows job copies `assets/logo.ico`, so it is in `SHA256SUMS.txt`), and `cli.js` passes `extras: ['fleet.ico']` to the kit's `installUpdate`, which replaces a file of that name only where an install put one, only if it matches the checksums, and never fails the update over it. Windows may keep showing the old icon until its icon cache refreshes. A new setup brings a new terminal.

## Rules

- Every app's cli keeps hosted mode working: streams from `appTerminal()`, given to Ink's `render` and `terminalMouse`; updates off when `hosted`; nothing written to the real terminal some other way. The app stays full-screen on the alternate screen, its frames starting at the top left corner.
- A new hand-off between apps goes through `copiedNote` (or calls `handOff` itself).
