# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

An Azure console for the terminal: App Service and Functions, their logs and their problems. Sonar is a keyboard-driven terminal app built with Ink (React for the terminal) on Node 22+. It was started from slipway, and it's a sibling of Splice (a git client) and Trawl (a SQL client). Plain JavaScript ES modules with `.jsx` for components; no TypeScript, no linter config. The README is the user-facing spec; when behaviour changes, update it too.

It lives in the fleet repository, in `apps/sonar`, and is built on the fleet's shared kit, `@fleet/kit` (`packages/kit`; the root CLAUDE.md has its rules): `text.js`, `ui/parts.jsx`, `ui/hooks.js`, `ui/HelpView.jsx`, `ui/Palette.jsx`, `mouse.js`, `selection.js`, `clipboard.js`, `jsx-hooks.js`, `register.js`, `help-layout.js`, `keymap.js`, `usercommands.js`, `palette.js`, `run.js`, `credentials.js`, `claude-cli.js`, `family.js`, `update.js`, `theme.js` and the build, the kit's `scripts/build.js`. Import them as `@fleet/kit/<file>`; Sonar keeps no copy of any of them, and a change to one is a change to every app, so run every app's tests (`npm test` at the root). Anything only Sonar needs lives in its own file (Sonar's `ui/Grid.jsx`). `src/app.js` tells the kit which app this is (`configureApp`: the name `sonar`, the title `Sonar`, the version a build bakes in); import `VERSION` and `COMPILED` from it. `src/theme.js` fills the kit's `theme` object with Sonar's palette.

## Commands

```bash
npm install                                                    # once, at the repository root: every app and the kit
npm test                                                       # whole suite (node:test), here; npm run test:sonar at the root
node --import @fleet/kit/register.js --import ./src/app.js --test test/units.test.js      # one file
node --import @fleet/kit/register.js --import ./src/app.js --test --test-name-pattern="settings" test/*.test.js   # tests matching a name
npm start                                                      # run from the checkout (needs a real TTY)
npm run build                                                  # Bun-compiled executable for this machine → dist/ (the kit's scripts/build.js)
node scripts/logo.js                                           # regenerate assets/ from src/pet.js
```

`--import @fleet/kit/register.js` is required whenever Node loads `.jsx`: it installs a module hook (the kit's `jsx-hooks.js`) that compiles `.jsx` with esbuild on import. There is no dev build step. The tests also preload `--import ./src/app.js`, so the kit knows the app before any test file loads. CI runs Sonar's tests on Linux and Windows whenever `apps/sonar` or the kit changes, so path handling and line endings must work on both (`.gitattributes` forces LF).

The Ink patch is the repository's (`patches/ink+6.8.0.patch` at the root, applied by `npm install` there); the root CLAUDE.md says what it does, and the kit's `test/ink-patch.test.js` checks it.

Releases are automatic: every push to main that changes `apps/sonar` (or the kit, `patches/` or the root package files; not Markdown-only ones) releases Sonar from the root Release workflow as `sonar-v<version>`: the newest `sonar-v…` release with the patch raised, or `package.json`'s version when that's higher (bump it there for minor or major). It sets the version in the runner before building and commits nothing back, so `package.json` on main lags behind the releases. Compiled builds get the version via `process.env.SONAR_VERSION` (defined by the kit's `scripts/build.js`, and written out in `src/app.js`), which also sets `COMPILED`; from a checkout `src/app.js` reads `package.json`, and the update check is skipped.

## Architecture

- **The provider**: everything Azure goes through one object with one interface, built in `cli.jsx`: `azure/arm.js` `createAzure({ fetch, token })` for real Azure (ARM for subscriptions, sites, slots, settings, restart/stop/start/swap, Application Insights components; the App Insights query API, classic schema, for telemetry), or `demo.js` `demoAzure()` for `--demo` and the tests. A new operation needs both, and a test of the ARM call against `fakeFetch` in `test/azure.test.js`. App takes it as the `provider` prop.
- **`src/azure/az.js`**: tokens from `az account get-access-token`, cached until five minutes before they run out; `az login` is the only sign-in. Sign-in trouble is said as "run az login".
- **`src/load.js`**: a subscription read whole (apps, every app's slots six at a time, components, container apps, storage accounts, SQL servers with their databases and Entra admin), which is `ctx.data`.
- **`src/cost.js`**: pure. This month's cost by resource (the provider's `costs(sub)`, Cost Management's MonthToDate ActualCost by ResourceId, read by `App`'s `costsOf` once a day and never again on `r`), per resource group (`groupCost`) and resource (`costOf`); a subscription whose costs can't be read says nothing of them.
- **`src/insights.js`**: pure. The queries Sonar sends (`problemsQuery`, `trendQuery`, `operationQuery`, `starterQuery`, `availabilityQuery`, `latestExceptionQuery`, `sqlDependenciesQuery`, `requestTraceQuery`, and `/compare-window`'s `compareQueries` over `windowsAround`, whose rows `compareWindows` reads), `componentFor` (an app's Application Insights, from its connection string or instrumentation key), `isProduction` (by app or resource group name, never the slot: every main slot is "production"), `looksSecret`, `settingsDiff`, `sparklines`, `completeQuery`, `cellText`. The demo's query engine (`demoQuery`) recognises the queries built here, so changing one means changing it too.
- **`src/metrics.js`**: pure. Azure Monitor's metrics for a site (`metricsPath`, `seriesFrom`, `metricRows` as sparklines through `sparklines`); the provider's `metrics(target, { span })` reads them, and `App`'s `metricsOf` keeps them per target and span until `r`.
- **`src/tree.js`**: the Resources view's rows (resource group headings; apps, slots, container apps, SQL servers and their databases, storage accounts), pure. Targets other than web apps carry a `type` (`container`, `storage`, `sqlserver`, `sqldb`); `ctx.selectedTarget()` is only ever a web app or slot, `ctx.selectedResource()` whatever is under the cursor.
- **`src/trawl.js`**: pure. SQL connection strings (`parseSqlConnectionString`), the login an app uses for a server (`findLogin`, never the password), the slash command `T` copies for Trawl's prompt (`trawlCommand`: `/azure-sql … --password-from <rg>/<app>[/<slot>]`, so Trawl reads the password from Azure itself), and the firewall (`ruleCovering`, `ruleName`). The public address comes from the provider's `publicIp()` (ipify, through its fetch).
- **`src/incident.js`**: pure. The incident view's parts (`I` in Problems, `/incident`; `actions.js` `gatherIncident` fetches them): the stack from an exception's `details` (`framesOf`), the deployments before it was first seen, the frames that are files in the checkout Sonar started in (`framesInCheckout`, then `gitLogCommand` through `run.js`; nothing when `repoRoot(cwd)` finds none), the contexts copied for Splice, Hail and Trawl, `incidentMarkdown` (what `s` saves before Claude's write-up and what Claude is given) and `writeupPrompt`. `TextViewer` takes `keys` and `hint` for views like it.
- **`src/watches.js`**: pure. `/watch` (`parseWatch`), the number a query answered (`watchValue`) and going over a threshold edge-triggered (`crossing`). Watches live in the config with the component they were made in; `App`'s `checkWatches` runs them every `watchEvery` minutes and notifies through the `notify` prop.
- **The family** (`@fleet/kit/family.js`, shared by all five apps and never edited here; `src/kin.js`, Sonar's own part, pure): everything copied for a sibling goes through `actions.js` `copyFor` (a plain command, or `takeLine`), never with a secret. `/take` (and a bare `family:v1:…` at the prompt, in `runLine`) is `actions.js` `take`. `pastedLine` is the paste rule in App's dispatcher. `familyChoices` is `/family`, over `projectAt(ctx.cwd())`. Ping's mood goes out through `familyMood` and `writeMood` whenever it changes, and `readMoods` is read every `familyEvery` ms (a prop; 30 s) for `reactionTo`; the `familyMoods` setting turns both off. Tests get a temporary `FAMILY_HOME` from `tempHome`. App's `cwd` prop (the folder Sonar started in) is `ctx.cwd()`, which tests set.
- **Changing Azure** (`actions.js`): every change goes through `confirmChange`, which asks for the app's name (`ctx.askText`) for production and for every swap, and a plain yes otherwise. Keep it that way for anything new that changes a resource. Settings are saved whole (ARM replaces the set), after `settingsDiff` has said what changes.
- **`@fleet/kit/run.js`**: the only place another program is started. Nothing it starts has a terminal, so nothing may wait on a prompt; an abort kills the whole tree (`taskkill /T` on Windows). Its `callSignal(signal)` gives one call (a fetch) a signal of its own under a long-lived one, tied to it only until `done()`, so many calls leave no listeners piled on it.
- **`src/actions.js`**: every user-facing operation, written once. Keys and slash commands call these with `ctx`. Questions before anything destructive live here (`ctx.confirm({ ..., danger: true })`).
- **`src/commands.js`**: the slash-command table (`name`, `args`, `desc`, optional `complete`, `run(ctx, rest)`) and completion. Args in `[brackets]` are optional, so picking the command runs it at once.
- **`src/ui/App.jsx`**: layout, focus, the prompt, overlays, the activity log and **`ctx`**: a stable object exposing `data` and `config` (getters), `task` (a visible, cancellable job with the spinner), `note`, `confirm`, `askSecret` / `askText` (a masked or plain field in the confirm's place), `prefill`, `showText` (text, or coloured `lines`), `showPicker`, `copy`, `setConfig`. A view that takes keys the app would otherwise use (a search being typed) sets `ctx.claimsKey(input, key)`, and clears it when it unmounts. Read the `Object.assign(ctx, {...})` block before adding an action.
- **`src/ui/*View.jsx`**: one component per tab: Resources, Logs (the query box, which claims every key while it's edited, and `Grid.jsx`), Problems, Live, Alerts (the provider's `alerts(sub, { span })`, Alerts Management's fired alerts, and `availabilityQuery` over the component in scope), Log. Logs and Problems show `scope` (App's `resolveScope`: the component and role name they look at). Views must check `ctx.viewHasKeys()` (or `ctx.overlayHasKeys()` in overlays) at the start of their `useInput` handlers. `useListNav` in `@fleet/kit/ui/hooks.js` is the shared cursor and scroll logic.
- **Claude** (`w` in Problems, `/why`): `actions.js` `why` sends a problem's latest occurrence (`occurrenceText`) through `claude-cli.js` `ask` with read-only `Read`, `Grep`, `Glob`, in the folder Sonar started in. `App` takes `ask` as the `askClaude` prop; tests stub it (`test/helpers.js` does by default).
- **Notifications** (`src/notify.js`, Trawl's): `App`'s `task` calls the `notify` prop when a job that wasn't cancelled took over `notifyAfter` seconds (10); `cli.jsx` writes the bell and OSC 9 / 777. The `notify` setting turns it off; tests pass a recorder or nothing.
- **Mouse** (`@fleet/kit/mouse.js`, `@fleet/kit/selection.js`; `apps/splice/docs/mouse.md` has the design): `terminalMouse` strips mouse reports out of stdin before Ink sees them and hands them to `App` as the `mouse` prop; tests pass a fake (`test/clicks.test.js`). Components register with `useMouse(ctx, handler)`; a view's rows start one line under its panel's top border. Views name their `useInput` handler `keys` so a double-click can call `keys('', { return: true })`.
- **Updates** (`@fleet/kit/update.js`): once a day, the newest `sonar-v…` release of the fleet repository, from GitHub's releases API, then `gh api` while the repository is private. A newer release is installed in the background next to the executable, checked against `SHA256SUMS.txt`. Release file names must match `buildTargets` in the kit's `update.js` (the kit's `scripts/build.js` builds those). `cli.jsx` passes `checkUpdate` and `installUpdate` only in compiled builds.
- **Config** (`src/config.js`): `~/.sonar/config.json`, overridable with `SONAR_HOME` (tests use it). Change it only through `ctx.setConfig`: `App` saves its whole copy. A new setting is a row in `src/settings.js` plus the README's Settings section.
- **Theme and text**: a dark and a light palette in `src/theme.js` (`applyTheme(config)` at start-up in `cli.jsx` and from Settings; `auto` reads `COLORFGBG`). Colours are read from `theme` while drawing: a module-level table of colours uses getters or a function, never values copied at import; use `BULLET` instead of `⏺`, and `@fleet/kit/text.js` (`fit`, `wrap`, `stringWidth`) for width-aware truncation, never `.length`.
- **Ping** (`src/pet.js`, `src/ui/Pet.jsx`): the mascot's pixel art and mood. `assets/` is generated from it by `scripts/logo.js`; don't hand-edit those files.

## Tests

`test/app.test.js` and `test/clicks.test.js` are end-to-end: they render `<App>` over a fresh `demoAzure()` with `ink-testing-library`, type keys into stdin and assert on `lastFrame()` and on the demo's state (`provider.state`). Nothing reaches Azure. `test/azure.test.js` covers the ARM client against a fake fetch, the az sign-in, the pure rules and the demo. Use `until(check, what)` from `test/helpers.js` to wait for frames rather than fixed sleeps. `test/units.test.js` covers the pure modules.

## Keeping things in sync

Adding or changing a key or command touches several places: the handler (view or `App.jsx`), `src/commands.js` for slash commands, the `?` window's sections in `src/help.js`, and the tables in `README.md`. Commit messages are short sentences describing the change, without type prefixes.
